# Журнал исследования

Скрипты в порядке, в котором шло исследование; папки — этапы. Каждый файл начинается с однострочного описания: что проверялось и что получилось.

Этапы 01–05 выполнялись локально (MacBook M4, 16 ГБ). Итоговое решение собирается ноутбуком [`../solution.ipynb`](../solution.ipynb) на GPU. Скрипты запускаются из корня репозитория после подготовки данных (`scripts/prep.py`, `build_tok.py`, `item_text.py`, `split.py`), например: `python experiments/01_eda/eda1.py`.

## [`01_eda/`](01_eda/) — разведочный анализ данных
| Скрипт | Вывод |
|---|---|
| `eda1.py` | 83% пар train — объявление из той же локации, что и поиск; только 5% объявлений train есть в корпусе бенчмарка; 37% текстов бенчмарка встречались в train |
| `eda2.py` | поиск по региону (107620 «Москва и область») ведёт в город (637640); у 17% запросов бенчмарка в их локации нет ни одного объявления корпуса |
| `eda3.py`, `eda4.py` | фильтры почти жёсткие: «Вид услуги» совпадает в 98.5% пар, «Тип услуги» — в 94.6%, рейтинг 4+ — в 99% |
| `eda5.py` | 9% запросов бенчмарка — `search_category=0` (в train почти нет); для них в корпусе лежат товары и вакансии («Аэрограф для ногтей», «Инженер ПТО») |
| `eda6.py` | корпус устроен как «все выбранные объявления отложенной части лога» — отсюда дизайн валидации в `scripts/split.py` |
| `eda7.py` | бенчмарк ≈ равномерная выборка по уникальным текстам: хвостовые запросы, 63% без фильтров |
| `loc_study.py` | потолок отбора по локации: та же локация — 77%, локации с P≥1% — 92% (медианный пул ~3k) → локация — приор, а не фильтр |

## [`03_local_pipeline/`](03_local_pipeline/) — дообучение энкодера и ранкер (попытка 1)
| Скрипт | Результат |
|---|---|
| `bench_step.py` | на MPS батч 128 уходит в своп → батч 64 (~1.8 с/шаг) |
| `ft_biencoder.py`, `encode.py` | дообученный e5-small: dense + локация 0.760 → **0.826** (+6.6 п.п.); этим скриптом обучены e5-small итогового решения |
| `run_feats.py`, `train_ranker.py` | LightGBM LambdaRank над кандидатами: 0.925 (zero-shot) → **0.944** (дообученный энкодер, символьные n-граммы, микрокатегории, kNN по логу) |
| `ranker_lc.py` | lambdarank 0.944 ≫ xendcg 0.916 ≫ binary 0.895; кривая обучения по числу запросов почти насыщена |
| `exp_ens.py` | шум ранкера по сидам ±0.2 п.п. → ансамбль из 3 сидов |
| `train_final_ranker.py`, `predict_bench.py` | финальный ранкер и инференс локальной версии → **попытка 1: LB 0.9163** |

## [`04_error_analysis/`](04_error_analysis/) — разбор ошибок и проверка гипотез
| Скрипт | Находка → действие |
|---|---|
| `miss_analysis.py` | семантические промахи («санобработка авто» → «Уничтожение клещей»), опечатки («иласос», «первозка») → дообучение энкодера, символьные 3-граммы |
| `miss2.py` | 81% не попавших в кандидаты — другие локации, глубоко в любой выдаче; однословные запросы — худший сегмент (0.916) |
| `extra_feats.py`, `exp_extra.py` | признаки «нелокальности» запроса: −0.17 п.п. → не вошли |
| `exp_robust.py` | без сырых счётчиков R@35 −0.5 п.п. → оставлены (с нормировкой на размер лога) |

## [`05_lb_gap/`](05_lb_gap/) — почему лидерборд ниже валидации
| Скрипт | Вывод |
|---|---|
| `diag_relevance.py` | разрыв val 0.945 → LB 0.916: определение релевантности то же (только по тексту было бы 0.795); состав запросов объясняет 0.3 п.п. |
| `diag_density.py` | корпус бенчмарка в ~1.45 раза плотнее → ~1.5 п.п.; новая метрика отбора — `R@35w` |

## [`06_notebook_addons/`](06_notebook_addons/) — дополнения к ноутбуку
Запускаются в ядре `solution.ipynb` после его разделов через `%run -i experiments/06_notebook_addons/<файл>`.

| Скрипт | Что делает |
|---|---|
| `fast_final.py` | быстрый финал на энкодерах, обученных на половине train (без переобучения на всём) → **попытка 2: LB 0.9239** |
| `adapt.py` | эксперимент: адаптация энкодера к корпусу без разметки (псевдо-пары «заголовок → объявление без заголовка»); в итоговый сабмит не вошёл |
